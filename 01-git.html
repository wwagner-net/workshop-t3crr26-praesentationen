Begriff

Was ist Git?

Git ist ein verteiltes Versionskontrollsystem. Es merkt sich jeden gespeicherten Stand deines Projekts.

  • 2005 von Linus Torvalds für den Linux-Kernel entwickelt
  • Open Source, läuft auf macOS, Linux und Windows
  • Arbeitet lokal, ohne Server und ohne Internet
  • Jede Kopie eines Repositorys enthält die komplette Historie

Drei Begriffe für heute

Repository („Repo“): dein Projektordner plus die komplette Historie (im versteckten Ordner .git).

Commit: ein gespeicherter Stand mit Nachricht, Autor und Datum.

Branch: eine Entwicklungslinie, zum Beispiel main.

  • „Verteilt“ heißt: Es gibt keinen zwingenden zentralen Server. Jede Kopie ist vollwertig.
  • Den Ordner .git nie von Hand anfassen oder löschen, sonst ist die Historie weg.
So funktioniert es

Vom Bearbeiten zum Commit

Mit git status siehst du jederzeit, was in welchem Bereich liegt.

  • Der Staging-Bereich ist der Punkt, an dem viele stolpern. Er erlaubt kleine, saubere Commits: nur die Änderungen am Header, nicht gleich alles.
  • Faustregel: ein Commit = eine logische Änderung, mit einer Nachricht, die erklärt, warum.
So funktioniert es

Commits bilden eine Kette, Branches sind Zeiger

Commit: Schnappschuss mit eindeutiger ID (Hash) und Verweis auf den Vorgänger.
Branch: ein beweglicher Zeiger auf einen Commit. Anlegen kostet nichts.
Merge: führt eine Linie wieder in main zurück.
  • Die Hashes sind in echt 40 Zeichen lang, Git zeigt meist die ersten 7.
  • Typischer Ablauf: neues Feature im eigenen Branch, testen, dann in main mergen. main bleibt immer deploybar. Das wird am Nachmittag wichtig.
Zusammenarbeit

Lokal und Remote

git clone holt eine komplette Kopie vom Remote.
git push schickt deine Commits zum Remote.
git pull holt neue Commits der anderen ab.
  • Das Remote ist technisch nur ein weiteres Repository. Es dient als gemeinsamer Treffpunkt.
  • Ausblick: Am Nachmittag ist der push auf main der Auslöser für das Deployment.
Spickzettel

Die Befehle, die du heute brauchst

# einmalig einrichten
$ git config --global user.name "Vorname Name"
$ git config --global user.email "du@example.com"

# Projekt unter Versionskontrolle stellen
$ git init
$ git remote add origin git@github.com:du/projekt.git
# der tägliche Kreislauf
$ git status
$ git add packages/sitepackage
$ git commit -m "Header-Navigation ergänzt"
$ git push

# Historie ansehen
$ git log --oneline

Branches: git switch -c feature/header legt einen an, git switch main wechselt zurück.

  • user.name und user.email stehen später in jedem Commit. Die E-Mail sollte zum GitHub-Konto passen.
  • Die Remote-Adresse beginnt mit git@: Das ist der Zugang per SSH. Wie der funktioniert, kommt in der nächsten Präsentation.
  • Unbedingt erwähnen: git checkout main und git checkout -b feature/header machen genau dasselbe wie switch bzw. switch -c. checkout ist der ältere Befehl, nicht veraltet und in vielen Anleitungen zu sehen. switch gibt es seit Git 2.23 und kann nur Branches wechseln. Damit ist ausgeschlossen, dass man aus Versehen Dateiänderungen verwirft, wie es bei git checkout -- datei passiert.
  • Wer lieber klickt: PhpStorm, VS Code oder GitHub Desktop machen dasselbe mit Oberfläche.
TYPO3-Praxis

Was gehört in dein TYPO3-Repository?

Rein damit

  • composer.json, composer.lock
  • packages/ (Sitepackage)
  • config/
  • .ddev/
  • deploy.php, .hosts.yml, Workflow

Draußen lassen

  • vendor/
  • public/ außer .htaccess
  • var/
  • .env, Datenbank-Dumps
# .gitignore (Auszug)
/vendor
/var/*
!/var/labels
/public/*
!/public/.htaccess
.env
database.sql
Server-Passwörter und API-Keys nie ins Repository. Die Historie vergisst nichts.
  • Grundregel: Code und Konfiguration rein, alles Erzeugte und alle Inhalte raus.
  • composer.lock unbedingt committen: Nur so landen auf dem Server exakt dieselben Versionen wie lokal.
  • public/* wird komplett ignoriert, weil in TYPO3 v14 fast alles darin erzeugt wird oder Inhalt ist: fileadmin, typo3temp, _assets, index.php. Nur die .htaccess wird mit ! wieder aufgenommen.
  • Die .gitignore ist ein Auszug aus dem Workshop-Projekt.
  • Die Server-Zugangsdaten stehen in der additional.php auf dem Server (in shared/) und kommen nie aus dem Repository. Mehr dazu in der Deployment-Präsentation.
Einordnung

Git ist nicht GitHub

Git ist das Werkzeug auf deinem Rechner. GitHub, GitLab & Co. sind Plattformen, die Remote-Repositories hosten und viel drumherum bieten.

⌂

Hosting

Das zentrale Repo, auf das alle pushen.

✓

Review

Pull Requests (GitHub) bzw. Merge Requests (GitLab) mit Kommentaren.

⚙

Automatisierung

GitHub Actions, GitLab CI: Tests und Deployment bei jedem Push.

🔑

Zugänge

Teams, Rechte, SSH-Schlüssel, Secrets für den Server.

  • Wichtig fürs Verständnis: Du kannst den Anbieter wechseln, ohne Git zu wechseln. Die Historie zieht einfach mit (git push zum neuen Remote).
  • Was nicht einfach mitzieht: Issues, Reviews und vor allem die CI-Konfiguration. Die ist anbieterspezifisch.

Für Git selbst ist es egal, wo das Remote liegt. Der Unterschied liegt in Komfort, Datenschutz, Kosten und Automatisierung.

  • Im Workshop nutzen wir GitHub, weil fast alle schon ein Konto haben und Actions im Rahmen kostenlos ist.
  • Der Ablauf lässt sich auf GitLab CI übertragen. Das Prinzip ist dasselbe, nur die Konfigurationsdatei sieht anders aus.
Entscheidung

SaaS oder self-hosted?

SaaS (GitHub, gitlab.com, Bitbucket …)

  • Sofort startklar, keine Wartung
  • Fertige Build-Server (Runner) inklusive
  • Große Community, viele fertige Bausteine
  • Code liegt beim Anbieter, oft außerhalb der EU
  • Kostenlose Kontingente sind begrenzt

Self-hosted (GitLab, Gitea, Forgejo …)

  • Volle Kontrolle über Daten und Standort
  • Erfüllt strenge Kunden- oder Behördenvorgaben
  • Keine Abhängigkeit von Preisen und Konditionen
  • Updates, Backups, Sicherheit liegen bei dir
  • Eigene Runner für die Automatisierung nötig

Faustregel: Ohne besondere Vorgaben ist SaaS der einfachere Start. Verlangt der Kunde Daten in eigener Hand, wird es self-hosted.

  • Fragen, die du dir stellen kannst: Gibt es Vorgaben vom Kunden (öffentliche Hand, Gesundheit)? Wer kümmert sich um Updates? Wie viele Build-Minuten brauche ich?
  • Mischformen gibt es auch, etwa gitlab.com mit eigenen Runnern im eigenen Rechenzentrum.
Zusammenfassung

Das nimmst du mit

  • Git speichert jeden Stand deines Projekts als Commit.
  • Branches trennen Arbeit, die noch nicht fertig ist.
  • Das Remote ist der gemeinsame Treffpunkt für alle.
  • GitHub, GitLab & Co. hosten das Remote und automatisieren Abläufe.
