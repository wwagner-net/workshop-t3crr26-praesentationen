Automatisch deployen

GitHub Actions meldet sich selbst auf deinem Server an und spielt den neuen Stand ein.

SSH steht für Secure Shell: eine verschlüsselte Verbindung zu einem anderen Rechner.

  • Statt Passwort nutzen wir ein Schlüsselpaar. Das ist bequemer und deutlich sicherer.
  • Viele Hoster (auch Shared Hosting) erlauben SSH-Zugang. Das ist die Voraussetzung für ein professionelles Deployment. Im Zweifel beim Hoster nachsehen oder nachfragen.
Das Prinzip

Ein Schlüsselpaar, zwei Rollen

🔑

Privater Schlüssel

~/.ssh/id_ed25519

  • Bleibt immer auf deinem Rechner
  • Wird nie verschickt, nie hochgeladen
  • Am besten mit Passphrase geschützt
🔒

Öffentlicher Schlüssel

~/.ssh/id_ed25519.pub

  • Darf jeder sehen
  • Hinterlegst du bei GitHub und auf dem Server
  • Funktioniert wie ein Schloss, das nur dein Schlüssel öffnet
Merksatz: .pub darf raus. Die Datei ohne Endung bleibt bei dir.
  • Asymmetrische Verschlüsselung: Was der private Schlüssel signiert, kann man mit dem öffentlichen prüfen. Aus dem öffentlichen lässt sich der private nicht berechnen.
  • Bild: Du verteilst Schlösser, die nur du öffnen kannst. Wer ein Schloss hat, kann dich trotzdem nicht ausgeben.
So funktioniert die Anmeldung

Beweisen, ohne den Schlüssel zu zeigen

Der private Schlüssel verlässt deinen Rechner dabei nie. Auf der Leitung ist nur die Signatur zu sehen.

  • Vereinfachte Darstellung, aber das Prinzip stimmt: Challenge, Signatur, Prüfung.
  • Darum ist ein abgefangenes Passwort ein Problem, ein abgefangener Anmeldevorgang mit Schlüssel aber nicht.
Schritt 1

Schlüsselpaar erzeugen

# gibt es schon einen Schlüssel?
$ ls ~/.ssh

# neues Paar erzeugen (Ed25519)
$ ssh-keygen -t ed25519 -C "wolfgang@laptop"

# Ergebnis
~/.ssh/id_ed25519      ← privat
~/.ssh/id_ed25519.pub  ← öffentlich
  • Ed25519 ist der aktuelle Standard: kurz, schnell, sicher.
  • Der Kommentar hinter -C hilft später zu erkennen, welcher Schlüssel von welchem Gerät stammt.
  • Nach einer Passphrase wird gefragt: Sie schützt den Schlüssel, falls dein Laptop verloren geht.
  • Funktioniert so auf macOS, Linux und Windows 10/11.
  • Wer schon einen Schlüssel hat (id_ed25519 oder id_rsa), kann ihn weiter nutzen. Nicht überschreiben, sonst sperrst du dich bei bestehenden Servern aus.
  • Bei ssh-keygen einfach Enter für den Standardpfad drücken.
Schritt 2

Öffentlichen Schlüssel hinterlegen

Bei GitHub

Profilbild → Settings → SSH and GPG keys → New SSH key. Inhalt der .pub-Datei einfügen.

$ cat ~/.ssh/id_ed25519.pub
# Verbindung testen
$ ssh -T git@github.com

Auf dem Server

Der Schlüssel landet in ~/.ssh/authorized_keys deines Server-Users. Oft geht das auch über das Kundenmenü des Hosters.

# macOS / Linux
$ ssh-copy-id user@server.example
$ ssh user@server.example
  • Beim GitHub-Test kommt eine Begrüßung mit deinem Benutzernamen und dem Hinweis, dass es keinen Shell-Zugang gibt. Das ist richtig so.
  • authorized_keys ist einfach eine Textdatei, ein öffentlicher Schlüssel pro Zeile. Zugang entziehen heißt: Zeile löschen.
  • Unter Windows gibt es ssh-copy-id meist nicht. Dann den Inhalt der .pub von Hand in authorized_keys einfügen oder das Hoster-Menü nutzen.
Die andere Richtung

Auch der Server weist sich aus

Beim ersten Verbinden zeigt SSH den Fingerabdruck des Servers und fragt nach. Mit yes wird er in ~/.ssh/known_hosts gespeichert.

Ab dann prüft SSH bei jeder Verbindung, ob es wirklich derselbe Server ist.

Ändert sich der Fingerabdruck, warnt SSH deutlich und bricht ab. Erst klären, warum (Serverumzug? Neuinstallation?), dann den alten Eintrag entfernen.
The authenticity of host 'server.example' can't be established.
ED25519 key fingerprint is SHA256:Xq3…
Are you sure you want to continue connecting (yes/no)? yes

# alten Eintrag entfernen
$ ssh-keygen -R server.example
  • Das schützt vor einem Angreifer, der sich als dein Server ausgibt.
  • Für den Nachmittag wichtig: GitHub Actions braucht diesen Eintrag ebenfalls. Dort erledigt das ssh-keyscan im Workflow.
Komfort

Weniger tippen: config und Agent

~/.ssh/config

Host kunde-live
    HostName server.example
    User web123
    IdentityFile ~/.ssh/id_ed25519

Danach reicht: ssh kunde-live

ssh-agent

Der Agent merkt sich deinen entsperrten Schlüssel, damit du die Passphrase nicht bei jedem git push eingibst.

$ ssh-add ~/.ssh/id_ed25519
# macOS: Passphrase im Schlüsselbund
$ ssh-add --apple-use-keychain ~/.ssh/id_ed25519
  • Die config ist besonders praktisch, wenn du viele Kundenserver hast: sprechende Namen statt IP-Adressen und Benutzernummern.
  • Die Option --apple-use-keychain gibt es nur unter macOS.
Im Workshop

Welcher Schlüssel liegt wo?

Für das Deployment erzeugst du ein eigenes Schlüsselpaar, ohne Passphrase. Der private Teil kommt als Secret zu GitHub, nie ins Repository.
  • Warum ein eigener Schlüssel? Er hat nur einen Zweck, liegt nur an einer Stelle und lässt sich jederzeit einzeln sperren, ohne deinen persönlichen Zugang anzufassen.
  • Ohne Passphrase, weil niemand da ist, der sie im automatischen Ablauf eintippen könnte. Der Schutz kommt hier über das verschlüsselte Secret bei GitHub.
  • Am Nachmittag: ssh-keygen -t ed25519 -f ~/.ssh/deploy_kunde -C "github-actions", dann privat als SSH_PRIVATE_KEY ins Repo-Secret und öffentlich auf den Server.
Sicherheit

Die wichtigsten Regeln

So machst du es richtig

  • Ein Schlüssel pro Gerät, ein eigener pro Deployment
  • Persönliche Schlüssel mit Passphrase
  • Nicht mehr genutzte Schlüssel bei GitHub und auf Servern entfernen
  • Rechte: Ordner ~/.ssh 700, privater Schlüssel 600

Das niemals

  • Privaten Schlüssel per Mail, Slack oder Chat schicken
  • Privaten Schlüssel ins Git-Repository legen
  • Einen Schlüssel im ganzen Team teilen
  • Warnungen zum Fingerabdruck einfach wegklicken

Laptop weg? Öffentlichen Schlüssel bei GitHub und in allen authorized_keys löschen. Damit ist der Zugang gesperrt.

  • Ist SSH bei zu offenen Rechten auf dem privaten Schlüssel unzufrieden, verweigert es die Nutzung mit einem Hinweis. Abhilfe: chmod 600 ~/.ssh/id_ed25519.
  • Wer ins Team kommt, erzeugt seinen eigenen Schlüssel. Wer geht, dessen Schlüssel wird entfernt. So bleibt nachvollziehbar, wer Zugang hat.
Zusammenfassung

Das nimmst du mit

  • Ein SSH-Schlüssel ist ein Paar: privat bleibt bei dir, öffentlich wird verteilt.
  • Der Server prüft eine Signatur, ein Passwort wird nicht übertragen.
  • known_hosts schützt dich vor falschen Servern.
  • Für das Deployment gibt es einen eigenen Schlüssel.
