Deployment verstehen

Begriff

Was ist Deployment?

Deployment heißt: einen geprüften Stand aus Git auf den Server bringen. Immer auf dieselbe Weise, ohne Handarbeit.

Reproduzierbar

Jedes Deployment läuft gleich ab, egal wer es auslöst.

Nachvollziehbar

Du weißt genau, welcher Commit gerade live ist.

Umkehrbar

Geht etwas schief, ist der alte Stand in Sekunden zurück.

  • Der Begriff klingt groß, die Idee ist einfach: den Weg auf den Server automatisieren.
  • Die drei Eigenschaften unten sind der Maßstab für alles Weitere.
Vorher und nachher

Vom FTP-Upload zum Workflow

Von Hand

  • Geänderte Dateien per FTP hochladen und hoffen, dass keine fehlt
  • composer install auf dem Server, falls das überhaupt geht
  • Während des Uploads ist die Seite halb alt, halb neu
  • Zurück zum alten Stand? Nur mit Backup und viel Zeit
  • Das Wissen steckt im Kopf einer einzigen Person

Automatisiert

  • git push auf main löst alles aus
  • Abhängigkeiten werden vorab gebaut und vollständig übertragen
  • Umgeschaltet wird erst, wenn alles bereitliegt
  • Rollback mit einem Befehl
  • Der Ablauf steht als Datei im Repository
  • Fragen: Wer deployt heute noch per FTP oder per SSH und git pull auf dem Server? Kein Vorwurf, das ist weit verbreitet.
  • Der letzte Punkt ist oft der wichtigste: Urlaub, Krankheit, neue Kollegen. Der Workflow ist dokumentiertes Wissen.
Was genau passiert

Die Schritte eines TYPO3-Deployments

# Schritt 4 im Workshop-Projekt: vor dem Umschalten im neuen Release
typo3 install:fixfolderstructure   typo3 extension:setup        typo3 upgrade:run
typo3 database:updateschema        typo3 referenceindex:update  typo3 language:update
typo3 cache:warmup --group system  # nach dem Umschalten: cache:flush --group pages
  • Gebaut wird auf dem Runner mit composer install --no-dev --no-scripts: keine Entwicklungspakete, und die Composer-Scripts laufen dort nicht, weil der Runner keine TYPO3-Datenbank hat.
  • Schritt 3 ist der Schlüssel: Redaktionsdaten und die Zugangsdaten in additional.php leben in shared/ und werden nur verknüpft. Sie werden nie überschrieben.
  • Schritt 4 läuft im neuen Release, bevor er live geht. Schlägt ein Befehl fehl, bricht das Deployment ab, und der alte Stand bleibt online.
  • Alle Befehle stehen als Tasks in der deploy.php und laufen über vendor/bin/typo3 mit /usr/bin/php8.5.
Wer macht was?

Drei Werkzeuge, drei Aufgaben

⎇

Git

Was wird deployt?

Der Commit auf main ist der Stand, der live gehen soll.

⚙

GitHub Actions / GitLab CI

Wann und wo?

Der Automat: startet bei jedem Push einen Build-Rechner, baut das Projekt und ruft Deployer auf.

⇪

Deployer

Wie kommt es auf den Server?

Lädt per rsync hoch, verknüpft, führt die TYPO3-Befehle aus, schaltet um.

Das Prinzip: Actions bzw. GitLab CI ist austauschbar, Deployer bleibt gleich. Deshalb lässt sich der Workflow leicht von GitHub nach GitLab übertragen.

  • Diese Folie ist die wichtigste der Präsentation. Wer die Arbeitsteilung verstanden hat, findet sich in jedem Setup zurecht.
  • Deployer läuft in unseren Projekten nur im Runner, nicht auf dem Laptop. Dadurch deployt jeder Push in derselben, sauberen Umgebung, unabhängig davon, wer ihn auslöst.
Deployer

So sieht es auf dem Server aus

/home/www/t3crr26/production/
├── releases/
│   ├── 3/
│   ├── 4/
│   └── 5/          ← neuester Stand
├── shared/
│   ├── public/fileadmin/
│   ├── public/typo3temp/
│   └── config/system/additional.php
└── current → releases/5

releases/: jedes Deployment bekommt einen eigenen, vollständigen Ordner. Die letzten paar bleiben liegen.

shared/: alles, was ein Deployment überleben muss. Wird in jeden Release verlinkt.

current: ein Symlink auf den aktiven Release. Umschalten heißt: diesen Link umbiegen.

Der Dokumentenstamm im Hosting zeigt auf current/public.
  • Deployer ist ein Open-Source-Werkzeug in PHP (deployer.org). Konfiguriert wird es in einer deploy.php im Projekt.
  • Den Dokumentenstamm stellst du einmalig im Hosting-Panel um. Ein falscher Stamm ist eine häufige Fehlerquelle beim ersten Deployment.
  • Der Pfad ist der aus dem Workshop-Projekt (deploy_path in .hosts.yml). Bei anderen Hostern sieht er anders aus.
  • additional.php legst du beim ersten Deployment einmal von Hand in shared/config/system/ an, mit den Datenbank-Zugangsdaten des Servers.
Deployer

Umschalten ohne Ausfall, zurück ohne Stress

  • Die Live-Seite läuft aus current weiter, während der neue Release vorbereitet wird.
  • Erst wenn alles bereitliegt, wird der Symlink umgestellt.
  • Bricht ein Schritt ab, bleibt der alte Stand einfach live.
# Deployer läuft nur im Runner. Zurück geht es so:

# 1. Standard: Commit rückgängig machen
$ git revert HEAD
$ git push           # neues Deployment

# 2. Schnell: Rollback-Workflow per Klick
# .github/workflows/rollback.yml
on: workflow_dispatch  # → dep rollback production

# 3. Notfall: per SSH auf dem Server
$ ln -sfn releases/4 current
Jeder Rollback setzt nur den Code zurück. Datenbankänderungen bleiben bestehen.
  • Wichtig: In unseren Projekten ist Deployer nur im GitHub-Runner installiert. dep rollback lässt sich deshalb nicht einfach vom Laptop aus aufrufen.
  • Weg 1, git revert: erzeugt einen neuen Commit, der die letzte Änderung rückgängig macht. Der Push löst ein ganz normales Deployment aus. Das dauert so lange wie ein Deployment, ist aber der sauberste Weg: Git und Server sind danach wieder auf demselben Stand.
  • Weg 2, Rollback-Workflow: eine zweite Workflow-Datei mit on: workflow_dispatch, die statt dep deploy den Befehl dep rollback production ausführt. Sie erscheint im Reiter „Actions“ mit einem Button „Run workflow“. Im Workshop-Projekt liegt sie als .github/workflows/rollback.yml: gleiche Secrets, gleiche concurrency-Gruppe wie das Deployment, damit beide nie gleichzeitig laufen. Composer-Abhängigkeiten braucht sie nicht, nur Deployer, deploy.php und .hosts.yml. Bei GitLab heißt das Gegenstück „manueller Job“: In der .gitlab-ci.yml des Projekts steht ein Job rollback mit when: manual. Er erscheint in jeder Pipeline von main mit einem Play-Button.
  • Weg 3, Notfall per SSH: im Deploy-Pfad current von Hand auf den vorherigen Release umbiegen, danach den Cache leeren. Achtung: main enthält dann weiter den fehlerhaften Stand. Der nächste Push deployt ihn erneut, deshalb zusätzlich Weg 1.
  • Wer möchte, kann Deployer auch lokal installieren (composer global require deployer/deployer:^8). Mit der .hosts.yml aus dem Repository und dem eigenen SSH-Schlüssel auf dem Server funktioniert dep rollback production dann auch vom Laptop.
  • Datenbank: Hat ein Update das Schema verändert, passt der alte Code eventuell nicht mehr dazu. Vor größeren Updates deshalb ein Datenbank-Backup. Wie viele Releases liegen bleiben, steuert keep_releases, im Projekt 5.
GitHub Actions

Der Workflow als Datei im Repository

# .github/workflows/deployment.yml (gekürzt)
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: shivammathur/setup-php@v2
        with: { php-version: '8.5', extensions: 'mbstring, intl' }
      - run: composer global require deployer/deployer:^8
      - uses: webfactory/ssh-agent@v0.10.0
        with:
          ssh-private-key: ${{ secrets.SSH_PRIVATE_KEY }}
      - run: ssh-keyscan -H ${{ secrets.SSH_HOST }} >> ~/.ssh/known_hosts
      - run: composer install --no-dev --no-scripts --prefer-dist
      - run: dep deploy production -vvv

on: Auslöser, hier jeder Push auf main.

runs-on: GitHub stellt einen frischen Linux-Rechner, den Runner.

steps: Code holen, PHP, Deployer, SSH-Schlüssel, dann das Projekt bauen.

secrets: der private Deploy-Schlüssel und der Servername, verschlüsselt bei GitHub hinterlegt.

Zum Schluss übernimmt Deployer.

  • Gekürzte Fassung der deployment.yml aus dem Workshop-Projekt: Namen der Schritte, mkdir/chmod für ~/.ssh und einige Composer-Optionen sind weggelassen.
  • concurrency: production in der echten Datei sorgt dafür, dass nie zwei Deployments gleichzeitig laufen.
  • Secrets legst du im Repository an unter Settings → Secrets and variables → Actions. In Logs werden sie automatisch ausgeblendet.
  • Den Verlauf jedes Laufs siehst du im Reiter „Actions“ im Repository. Dort steht auch, an welchem Schritt es gehakt hat.
Alles zusammen

Vom Push bis zur Live-Seite

  • Einmal langsam von links nach rechts durchgehen und die Verbindung zu den beiden vorherigen Präsentationen herstellen: links Git, rechts SSH.
  • Die Dauer hängt vom Projekt und vom Hoster ab. Die Angabe ist ein Erfahrungswert, keine Garantie.
GitLab CI

Dasselbe Prinzip mit GitLab

# .gitlab-ci.yml (gekürzt)
deploy:
  stage: deploy
  image: php:8.5-cli
  resource_group: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"
          && $CI_PIPELINE_SOURCE == "push"'
  before_script:
    # git, rsync, ssh, intl, Composer installieren …
    - composer global require deployer/deployer:^8
    - eval "$(ssh-agent -s)"
    - echo "$SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -
    - ssh-keyscan -H "$SSH_HOST" >> ~/.ssh/known_hosts
  script:
    - composer install --no-dev --no-scripts
    - dep deploy production -vvv

Deployer und deploy.php bleiben gleich.
  • Gekürzte Fassung der .gitlab-ci.yml aus dem Workshop-Projekt. Der größte Unterschied: Das PHP-Image bringt wenig mit, deshalb installiert before_script erst git, rsync, den SSH-Client, die intl-Erweiterung und Composer.
  • Den SSH-Agenten startet der Job selbst, statt einer fertigen Action. Die Variablen SSH_PRIVATE_KEY und SSH_HOST heißen genauso wie die Secrets bei GitHub.
  • Deployment und Rollback teilen sich in der Projektdatei einen versteckten Job .deployer (Image, resource_group, before_script), den beide per extends erben. Der Rollback ist ein manueller Job mit allow_failure: true, sonst stünde jede Pipeline auf „blocked“, bis jemand ihn startet.
  • Bei selbst gehostetem GitLab braucht es einen eigenen Runner. Das ist meist die größte Hürde, nicht die YAML-Datei.
Praxis

Typische Stolperfallen

Dokumentenstamm

Zeigt noch auf den alten Ordner statt auf current/public.

Falsche PHP-Version

Auf der Kommandozeile des Hosters läuft eine andere PHP-Version als im Web. Pfad zur richtigen CLI angeben.

Fehlende Shared-Dateien

additional.php mit den Zugangsdaten liegt beim ersten Deployment noch nicht in shared/config/system/.

known_hosts fehlt

Der Runner kennt den Server nicht und bricht ab. ssh-keyscan im Workflow nicht vergessen.

  • Das sind die häufigsten Gründe, wenn das erste Deployment hakt. Die Fehlermeldungen im Actions-Log führen meist direkt hin.
  • Zur PHP-Version: Bei manchen Shared-Hostern muss der volle Pfad angegeben werden. Im Workshop-Projekt steht dafür set('bin/php', '/usr/bin/php8.5') in der deploy.php.
Zusammenfassung

Das nimmst du mit

  • Deployment ist der automatisierte Weg von Git auf den Server.
  • Git sagt was, Actions / GitLab CI sagt wann, Deployer sagt wie.
  • Releases, shared/ und der Symlink current machen Umschalten und Rollback sicher.
  • Der ganze Ablauf liegt als Datei im Repository.

Jetzt in die Praxis

Wir richten das zusammen ein: Repository, Deploy-Schlüssel, Secrets, deploy.php und Workflow. Am Ende steht dein erstes automatisches Deployment.
